# Spike findings for 0.0.1

Environment: Apache Airflow **3.2.2** (same version as production), Python 3.12, `airflow standalone` with the **simple auth manager**, LocalExecutor, macOS. Spike date: 2026-10-03. Raw output: one JSON line per callback, collected through a file sink, because the DAG processor rewrites its per-file log on every parse and drops `print` output.

## Changes required before Phase 1 (review gate)

1. **S2 is a go, through the Task SDK runtime and not REST.** `RuntimeTaskInstance.get_task_states(dag_id=..., run_ids=[run_id])` works from task callbacks *and* from DAG callbacks (the DAG processor proxies it), with no HTTP and no credentials. Delete `RestTaskStateReader`, the `chappe_airflow_api` connection and the `httpx` dependency (Tasks 3, 16, 17, Global Constraints).
2. **The runtime read returns states only.** The shape is `{run_id: {task_id: state}}`. It has no `start_date`, `end_date` or `try_number`. `TaskRecord(state, started_at, ended_at)` in Task 16 cannot be filled for steps other than the one that raised the event. **Decision needed** (see "Open decision" below).
3. **The DAG processor accepts only a subset of runtime calls.** In 3.2.2 it accepts `GetConnection`, `GetVariable`, `GetTaskStates`, `GetTICount`, `GetPreviousDagRun`, `GetPreviousTI`, `GetPrevSuccessfulDagRun` and the XCom calls. `get_dagrun_state` and `get_task_breadcrumbs` are **not** accepted: the supervisor logs `Unable to decode message … GetDagRunState`, and the callback hangs until the processor times out it, which delays the next DAG callback for that file by about 80 s. Chappe must call only `get_task_states` and `Connection.get` from DAG callbacks, and must take the run state from `context["dag_run"].state`.
4. **Callbacks see their own task state with a lag.** In `on_failure_callback`, the failing task still reads `running`. In `on_success_callback`, it already reads `success`. The source must overlay the callback's own outcome on the state it reads (Task 16/17).
5. **The DAG-callback context has two shapes.** When the server sends `last_ti`, it is a full template context plus `reason`. Otherwise it is only `{"dag", "run_id", "reason"}`, with **no `dag_run`** (`airflow/dag_processing/processor.py`, `_execute_dag_callbacks`). The notifier must read `run_id` from `context["run_id"]` and survive a missing `dag_run`. Every observed run had the full shape.
6. **The minimum Airflow version is 3.2** for 0.0.1 (verified version: 3.2.2). The DAG processor's message union differs between minors. Supporting older versions needs its own check.
7. **The 0.0.1 store is an Airflow Variable, not Slack message metadata** (ADR-0005). The workspace app has only `chat:write`, and adding `channels:history` / `groups:history` needs a reinstall and possibly admin approval. `Variable.get` / `Variable.set` work from task callbacks and DAG callbacks, so Task 13 becomes `AirflowVariableStore` behind the same `Store` port. The Slack bot then needs `chat:write` only. Chappe still writes its metadata on every message, which keeps the Slack metadata store possible later.

## Open decision: step times without REST

The runtime read gives states only. Today the plan uses `started_at` / `ended_at` for step durations in the thread history, for "running for 30m", and for `Watermark.last_change`.

| Option | What it costs | What is lost |
|---|---|---|
| **A. States from the runtime; times only from the event's own task instance and `dag_run`** (recommended) | Nothing new. `StepView.started_at` / `ended_at` are already optional. | Durations for steps whose event Chappe did not process directly. Thread replies are written when their own event happens, so they still carry their duration; only the parent's step list goes without. `Watermark.last_change` uses the event's own timestamp. |
| B. A plus `get_task_breadcrumbs` in task callbacks | A few lines in the source | Durations of finished steps in task callbacks only. The final DAG callback still has no durations (call unsupported there), so the final parent differs from the in-run ones. |
| C. Keep REST for dates, runtime for states | Keeps `httpx`, the `chappe_airflow_api` connection, and the auth-manager risk | Nothing, but it keeps the dependency that change 1 removes |

| S7 (new): Airflow `Variable` read-modify-write from callbacks | Works in task callbacks and in DAG callbacks (the DAG processor accepts `GetVariable` / `PutVariable`). JSON round-trips. 11–25 ms per get + set + get. | `variable_rw` in all seven callback lines of two runs: tags accumulate `task_execute → task_success → task_failure → dag_failure` in one Variable per run | Change 7 |

Observations for Phase 2:

- A failed run shows "4/4 steps", because a failed step counts as finished. "3/4 passed" or "failed at Regression checks" would read better.
- The parent is edited in place with `chat.update`, so edits do not notify; the broadcast final reply and the alert carry the notification, as designed.
- The real DAG-processor context includes `params`, so the final title renders from the template (the minimal-context fallback was not hit).
