> **Principle.** Chappe never breaks or blocks a pipeline. It prefers being late over being wrong, and silence over a duplicate.

This principle is the headline of the README and the landing page. Every design decision below is checked against it.

The name comes from Claude Chappe's optical telegraph (1790s France), a chain of towers that relayed a message station by station. Chappe does the same for a pipeline: each milestone is a tower, a theme decides what the signal looks like, and the message travels along the line.

---

## 1. Summary

Chappe is an open-source library that reports the progress of Apache Airflow runs to chat, starting with Slack. A run gets **one channel message that updates in place**, with step-by-step history in **that message's thread**. DAG authors mark the tasks that matter with one decorator. Everything else (channel, theme, icons, storage) is configuration.

### Goals

- One channel message per process, edited in place; detail in its thread. Parallel runs never interleave.
- Only tasks marked as milestones appear, under a display name chosen by the DAG author.
- Zero notification code in DAGs beyond the `@milestone` marker.
- Configurable, extensible themes: swap icons and labels in YAML; write new layouts in Python.
- Pluggable components (theme, store, transport, linker, source) behind versioned interfaces, discoverable as separate packages.
- A test kit that defines what a correct component is and lets third parties prove it.
- Built as an open-source project from day one: nothing in the code is specific to one company, channel, emoji set or workflow.

### Non-goals for 0.0.1

- Plugin mode (listeners); 0.0.1 attaches through notifier mode only (0.0.2).
- Built-in themes beyond `thread` and `plain` (0.0.2).
- Processes spanning several DAGs (0.0.3).
- Retry and repair history (0.0.4).
- Mapped tasks (`expand()`): one step with many instances is not modelled yet.
- Theme changes during an in-flight run: changing a process's theme or tokens while it runs is the developer's responsibility; Chappe does not pin themes per run.
- Transports other than Slack; stores other than Slack message metadata.
- Charts, Slack Block Kit layouts, colored attachment edges.
- Airflow 2.x.

## 2. Background

Teams often report pipeline progress by posting one chat message per step. With several runs in parallel the channel becomes a stream that readers untangle by matching version strings by eye. Step counters like "[3/5]" assume every run has the same steps, durations are left for the reader to compute, there are no links, and a failure looks the same as silence.

An exploration of formats (published as two private mock-up pages) settled on: one message per run, edited in place; a thread for history; status emoji instead of colored bars; plain formatted text rather than Block Kit; on-call mentioned in a thread reply because Slack does not notify on edits. A real Slack test of the native `plan` block showed it is collapsed by default, uses small grey text and renders done and pending steps identically, so it is not used.

## 3. Vocabulary

| Term | Meaning | 0.0.1 source in Airflow |
|---|---|---|
| **Process** | What one channel message represents. Defined in config as one or more DAGs | One DAG run (multi-DAG linking in 0.0.3) |
| **Section** | A group of steps within a process | See 4.1.1; task groups are optional |
| **Step** | A milestone worth reporting | A task marked `@milestone` |
| **Attempt** | One try of a step | Always one in 0.0.1 |
| **Theme** | Turns a process into messages | Built-in or third-party |
| **Capability** | An optional feature a component declares it supports | `MULTI_SOURCE` (0.0.3), `ATTEMPTS` (0.0.4) |

## 4. User experience

### 4.1 Marking milestones

```python
from airflow.sdk import dag, task, task_group
from chappe import milestone

@dag(schedule=None, params={"product": "orders", "version": "2026.10.1"})
def regression():

    @task_group(group_id="prepare")          # section "Prepare"
    def prepare():

        @milestone("Parquet → Delta")        # reported under this name
        @task
        def convert(): ...

        @task                                # not a milestone: never reported
        def cleanup_tmp(): ...

        @milestone("Geometry")
        @task
        def geometry(): ...

        convert() >> cleanup_tmp() >> geometry()

    prepare()

regression()
```

Classic operators use the same marker as a call:

```python
milestone(BashOperator(task_id="aggregates", bash_command="..."), "Aggregates")
```

`milestone(title=None, *, section=None)`: `title` defaults to the task's `task_display_name`, then its `task_id`. The marker is stored in a field Airflow serializes, so the scheduler sees it (verified in spike S1).

#### 4.1.1 Sections

Task groups are optional. A milestone's section is resolved in this order:

1. `section=` on `@milestone`.
2. `section` in the config's `milestones:` override.
3. The milestone's **outermost** task group, so nested groups do not multiply sections.
4. The DAG's default section: named after the DAG's `section:` entry in config, or after the DAG id.

A DAG without task groups or `section=` arguments yields one section holding every milestone in dependency order. When a process has a single section, themes omit the section header, so the message reads as a flat list of steps. A task group that contains no milestones never becomes a section, so groups used only to organize code stay invisible.

A section's **title** is resolved in this order:

1. `title` in the config's `sections:` override.
2. The text given to `section=` on `@milestone`, when the section came from there.
3. The task group's `group_display_name`, Airflow's built-in display name for groups (its presence and serialization are checked in spike S1).
4. The group id made readable (`prepare_data` → "Prepare data"); for a DAG's default section, its `section:` from config, else the DAG id made readable.

Each section also has a stable **key** (the group id, the `section=` text, or the DAG id) that is independent of its title, so renaming a title never changes message keys or thread history. No decorator for task groups is added; a `@section` decorator can be considered later if teams ask for one.

### 4.2 Two ways to attach

**Notifier mode (0.0.1).** One line per DAG:

```python
from chappe.integrations.airflow import ChappeNotifier

@dag(on_success_callback=ChappeNotifier(process="regression"),
     on_failure_callback=ChappeNotifier(process="regression"))
```

`ChappeNotifier` is a `BaseNotifier`, so it is used like any Airflow notifier. In notifier mode, `@milestone` also attaches the task-level callbacks needed for step events.

All Chappe work in notifier mode runs in task and DAG callbacks, never in the scheduler. At worst a slow Slack adds a few seconds to a callback; it cannot slow scheduling.

**Plugin mode (0.0.2, after performance testing).** Installing the package registers a provider and, through it, a listener plugin (the pattern used by Airflow's OpenLineage provider), so DAGs only carry `@milestone` markers. Listeners for run events execute inside the scheduler, which decides what runs next for every DAG. Rendering, theme code or Slack calls there would let one slow or faulty component slow scheduling for all pipelines. Plugin mode therefore ships only once its listeners can **record an event and return**, with all rendering and sending happening outside the scheduler; how is decided by performance testing and the spike for 0.0.2.

Both modes share the same core, configuration and themes.

### 4.3 Configuration

The config file is located through the provider's Airflow config option `[chappe] config_file` or the `CHAPPE_CONFIG` environment variable. Secrets are never in it.

```yaml
chappe:
  enabled: true
  defaults:
    transport: { type: slack, connection_id: chappe_slack }   # Airflow connection holds the token
    store: { type: slack_metadata }
    theme: { name: thread }
    time: { timezone: UTC, duration_format: short }
  processes:
    regression:                       # referenced by ChappeNotifier(process=...)
      dags:                           # one or more DAGs; 0.0.1 accepts exactly one
        - dag_id: regression
          section: "Regression"       # optional: default section name for this DAG
      link:                           # 0.0.3: how runs of these DAGs find each other
        key: "{{ params.product }}/{{ params.version }}"
      channel: "#pipeline-runs"
      title: "{{ params.product }} {{ params.version }}"
      theme:
        name: thread
        tokens:
          extends: thread
          icons: { running: ":loading:", done: ":heavy_check_mark:" }   # custom workspace emoji
      alerts:
        mention: "<!subteam^S00000000>"   # placeholder: a user group to notify on failure
        on: final_failure
      sections:                         # optional section title overrides, keyed by section key
        prepare_data: { title: "Prepare" }
      milestones:                       # optional overrides, no DAG change needed
        geometry: { title: "Generate geometry" }
        cleanup_tmp: { hidden: true }
```

The process, not the DAG, is the unit of configuration. The schema above is final from 0.0.1, so 0.0.3 adds behavior without changing users' config. In 0.0.1 a process must list exactly one DAG and `link` is ignored; a process with several DAGs fails validation with an error stating that multi-DAG processes arrive in 0.0.3.

`chappe validate-config` validates the file in CI (0.0.1). `chappe list-components` and `chappe preview` follow in 0.0.2.

### 4.4 Built-in themes

| Theme | Release | Layout |
|---|---|---|
| `thread` (default) | 0.0.1 | Header, one progress row of icons per section, current step line; step history in the thread |
| `plain` | 0.0.1 | Minimal text; also the fallback when a theme fails |
| `metro` | 0.0.2 | Vertical line of steps per section, connector glyphs between stations |
| `now_next` | 0.0.2 | What is running now and what comes next, progress bar, elapsed time |
| `tree` | 0.0.2 | One line per section: step icons, then label and status |

Default tokens use standard Unicode emoji so the themes work in any workspace (`:hourglass_flowing_sand:` running, `:white_check_mark:` done, `:x:` failed, `:white_circle:` pending). Workspaces override them with custom emoji in YAML. Themes must not rely on color or animation alone: every state also has a word or a distinct shape.

## 5. Architecture

### 5.1 Ports and adapters

- **Core** holds the domain model, the run view, the message set, the engine and the reconciler. It imports neither Airflow nor Slack; `import-linter` enforces this in CI.
- **Ports** are small `typing.Protocol` interfaces: `Source`, `Theme`, `Transport`, `Store`, `Linker`. Each has a contract version and a conformance suite.
- **Adapters** implement ports: the Airflow source and integration, the Slack transport, the Slack message-metadata store, the single-run linker, the built-in themes.
- **Registry** discovers adapters through Python entry points, so third-party packages (for example `chappe-teams`) are picked up when installed:

| Entry point group | Example |
|---|---|
| `chappe.themes` | `metro = chappe.themes.builtin.metro:MetroTheme` |
| `chappe.stores` | `slack_metadata = chappe.stores.slack_metadata:SlackMetadataStore` |
| `chappe.transports` | `slack = chappe.transports.slack:SlackTransport` |
| `chappe.linkers` | `single_run = chappe.linkers.single_run:SingleRunLinker` |
| `chappe.sources` | `airflow = chappe.integrations.airflow.source:AirflowSource` |

- **Capabilities.** Each component declares a `frozenset[Capability]`. The engine refuses a configuration whose components cannot support what it asks for, at load time, with an error naming the component and the missing capability.

## 6. Domain model and theme contract

### 6.1 Run view

Immutable, typed, free of Airflow types.

```python
class ProcessState(Enum): PENDING; RUNNING; SUCCEEDED; FAILED
class StepState(Enum): PENDING; RUNNING; SUCCEEDED; FAILED; SKIPPED

@dataclass(frozen=True, slots=True)
class ProcessView:
    key: str                       # "dag_id/run_id" in 0.0.1
    title: str
    state: ProcessState
    started_at: datetime | None
    ended_at: datetime | None
    now: datetime                  # render clock; themes never read the system clock
    sections: tuple[SectionView, ...]
    links: tuple[Link, ...]
    watermark: Watermark           # how far along this view is; see 7.1
    # derived: duration, progress, current_steps, next_steps, failed_steps

@dataclass(frozen=True, slots=True)
class SectionView:
    key: str
    title: str
    state: ProcessState
    steps: tuple[StepView, ...]

@dataclass(frozen=True, slots=True)
class StepView:
    key: str
    title: str
    state: StepState
    started_at: datetime | None
    ended_at: datetime | None
    error: str | None              # trimmed, safe to show
    links: tuple[Link, ...]
    attempts: tuple[AttemptView, ...]
```

The Airflow adapter maps Airflow states to these: `queued`/`scheduled`/`none` → `PENDING`; `running`/`up_for_retry`/`up_for_reschedule`/`deferred` → `RUNNING`; `success` → `SUCCEEDED`; `failed`/`upstream_failed` → `FAILED` (with `error` naming the upstream failure for the latter); `skipped`/`removed` → `SKIPPED`. A process is `FAILED` when the DAG run failed, `SUCCEEDED` when it succeeded, otherwise `RUNNING` once any step started.

Step order within a section is the DAG's dependency order restricted to milestones, ties broken by declaration order. Sections are ordered by their first step; in multi-DAG processes (0.0.3), by the order of `dags:` in config. Section resolution follows 4.1.1, and themes omit the section header when a process has one section (theme rule 8). Parallel branches render in that order; a dedicated representation is an open question (section 14).

### 6.2 Theme contract (version 1)

```python
class Theme(Protocol):
    name: ClassVar[str]
    contract_version: ClassVar[int]                 # 1
    capabilities: ClassVar[frozenset[Capability]]

    def render(self, view: ProcessView, ctx: RenderContext) -> MessageSet: ...
```

- `RenderContext` carries resolved **tokens** (icons, labels, colors, formats, timezone, limits) and a **formatter** supplied by the transport (`bold`, `italic`, `link`, `icon`, `mention`, `escape`, `duration`, `time`). Themes never emit transport syntax directly; this keeps them transport-neutral, and the formatter escapes DAG-supplied text.
- `MessageSet`:
  - `parent: ParentMessage(text, fallback_text)`
  - `thread: tuple[ThreadEntry(key, text, broadcast: bool), ...]`, ordered
  - `alerts: tuple[Alert(key, text, target), ...]`
- Keys are stable identifiers such as `step:geometry:succeeded` or `process:failed`. Reconciliation relies on them.

### 6.3 Tokens

Each built-in theme ships a token file. A user token block names `extends:` and overrides keys. Validation at load time rejects unknown keys and missing required tokens, naming the key.

### 6.4 Theme rules (enforced by the conformance suite)

1. Pure and deterministic: same view and tokens give the same output; no I/O, clock or randomness.
2. Every process and step state renders, and no state is distinguished by color alone.
3. Parent and thread entries stay within configurable limits (default parent limit well below Slack's maximum, for readability).
4. A failed process always produces at least one alert.
5. Thread entry and alert keys are stable across renders of the same state.
6. Declared capabilities are backed by passing the matching sample runs.
7. The engine refuses a theme whose `contract_version` is newer than it supports.
8. A process with a single section renders without a section header.

## 7. Event flow

```
① hook → ② ChappeEvent → ③ filter → ④ link → ⑤ snapshot → ⑥ load sent state (skip if unchanged)
       → ⑦ render → ⑧ key diff → plan → ⑨ send + save
```

1. **Hook.** Airflow events arrive from listeners (plugin mode) or callbacks (notifier mode):

| Event | Notifier mode (0.0.1) | Plugin mode (0.0.2) |
|---|---|---|
| Run started | first milestone's `on_execute_callback` | `on_dag_run_running` (record and return only) |
| Step started / finished | task callbacks attached by `@milestone` | `on_task_instance_running/success/failed` |
| Run finished | DAG `on_success/on_failure_callback` | `on_dag_run_success/failed` (record and return only) |

2. **Normalize** to `ChappeEvent(kind, source, run_ref, step_key | None, state, occurred_at)`.
3. **Filter.** Unconfigured DAGs and non-milestone tasks stop here.
4. **Link.** The linker maps the run reference to a process key (`dag_id/run_id` in 0.0.1).
5. **Snapshot.** The source reads milestones, sections and order from the DAG, and states and times of milestones from Airflow. The triggering event's state overrides what was read, since a callback may run before Airflow saves the task's new state. The title template is rendered from the run's params.
6. **Load sent state** from the store: parent message reference, parent text hash, sent thread and alert keys, stored watermark. If the new view's watermark is not newer than the stored one, stop (7.1).
7. **Render** with the configured theme. On exception, render with `plain` and log the theme error.
8. **Diff.** Parent: post if absent, edit if the text hash changed and the write rules allow it (7.1). Thread entries and alerts: send keys not yet sent, in order.
9. **Send and save.** The transport executes the plan; the store saves after each successful call, so a partial failure is completed by the next event without resending.

### 7.1 Write safety

Every event re-reads the full state from Airflow, so each render is correct when it is computed. The danger is the order in which writes reach Slack: Slack keeps whichever edit arrives last, so a render computed earlier but delivered later overwrites a newer one. At the end of a normal run, the last milestone's callback can read the run as still running while the DAG's success callback renders "Passed"; if the first one's edit lands second, the message would show "in progress" forever. Four rules prevent this:

1. **Watermark.** Each view carries a watermark: the latest state change it reflects, and whether the process has finished. The watermark is stored with the message, and a render never replaces a newer one.
2. **Finished is sticky.** A render that has not seen the process finish never replaces one that has.
3. **Final check.** After the final event writes the result, it waits briefly, reads the message back once and rewrites it if a late writer slipped in. This covers the only case no later event can repair.
4. **Duplicate parents heal themselves.** After creating a parent, the event looks again; if two parents exist for the same process, the earliest wins and the later one is deleted by the bot.

With the Slack metadata store these rules leave a window only when two non-final writers read and write within the same fraction of a second; the next event or the final check repairs it. A store with true compare-and-set (Postgres, later) enforces rules 1, 2 and 4 atomically.

## 8. Storage

### 8.1 Store port

```python
class Store(Protocol):
    contract_version: ClassVar[int]
    capabilities: ClassVar[frozenset[Capability]]

    def load(self, process_key: str) -> SentState | None: ...
    def save(self, process_key: str, state: SentState, *, expected_version: int | None) -> int: ...
```

`save` is compare-and-set where the store supports it: it fails with `StoreConflict` when the stored version differs from `expected_version`. Stores that cannot guarantee it atomically declare so, and the engine relies on the write rules in 7.1.

### 8.2 0.0.1: Slack message-metadata store

The sent state (process key, watermark, parent text hash, sent keys) is attached as hidden metadata to the parent message itself. Any event, from any task or DAG callback, finds the message by scanning the bot's recent messages in the channel for that process key. It needs no infrastructure and nothing in Airflow, cannot be wiped by clearing a task, and works wherever the Slack token works. Costs and limits: one extra Slack read per event; only messages within the scanned recent history are found, which suits runs of hours to days; no atomic compare-and-set, so the write rules in 7.1 apply.

XCom was the original choice and is rejected: XCom belongs to a task instance, so DAG-level callbacks may be unable to reach it, and clearing the owning task deletes it. Under "silence over a duplicate", an unreachable store would mean a run's result is never posted.

### 8.3 Later stores

| Store | Survives a clear | Spans DAGs | Infrastructure |
|---|---|---|---|
| Postgres, own database (strategic) | Yes | Yes | A Postgres server |
| Redis | Yes | Yes | Redis |
| Object storage file | Yes | Yes | A bucket |

Postgres is the long-term direction: it gives atomic compare-and-set, and the same database can keep a history of every run with step timings for dashboards and analysis. Delivery state and run history are separate concerns and get separate interfaces: the `Store` port for delivery state, and a future **history recorder** port fed by the same events. One Postgres package can implement both, and teams can use either without the other.

Rejected: XCom (above), Airflow Variables (clutter a list people rely on), DAG run notes (visible and editable), Airflow's metadata database (not allowed for task code in Airflow 3; owned by Airflow's migrations), a watcher task added to each DAG (single writer, but changes the DAG).

## 9. Error handling

Applies the principle: never break or block, late over wrong, silence over duplicate.

### 9.1 Configuration errors

Validated at load: structure, component names, capabilities, token completeness, title templates, override task ids. On error Chappe disables itself for the affected DAG only and logs the file, key and fix. It never raises into the scheduler, DAG import or a task. `strict=True` and `chappe validate-config` raise instead, for CI.

### 9.2 Runtime errors

| Stage | Handling |
|---|---|
| Snapshot fails | Skip the event and log; the next event heals |
| Store unreadable | Skip sending: without knowing whether a parent exists, posting risks a duplicate |
| Theme raises | Render with `plain`; log theme and error |
| Transport, retryable (rate limit, 5xx, timeout) | Retry with backoff honoring `Retry-After`, within the event's time budget; otherwise leave to the next event |
| Transport, permanent (`channel_not_found`, `not_in_channel`, `invalid_auth`) | Log once per process, mark the process degraded in the store, stop for that process |
| Parent message deleted | Post a new parent and update the store |
| Store write fails after a send | Log; the next event may resend that entry (documented, rare) |
| Late writer overwrites newer state | Prevented by the write rules in 7.1; the final event's read-back repairs the last case |

### 9.3 Time budgets

Every event has a configurable time budget (default 10 s). The **final event** of a process (run succeeded or failed) gets a larger budget, additional retries with backoff and the read-back check from 7.1, since no later event can correct it. If it still fails, Chappe logs an error with the process key.

### 9.4 Kill switch

`enabled: false` globally or per process, and the `CHAPPE_ENABLED=false` environment variable, take effect without code changes.

## 10. Security

- The Slack token lives in an Airflow connection or secrets backend, never in YAML, code or logs.
- The formatter escapes all DAG-supplied text (titles, step names, error text).
- Error text sent to chat is trimmed and never includes stack traces.
- Third-party components run in-process with Airflow's permissions; the docs say so plainly and recommend installing only trusted components.

## 11. Observability

- Structured logs; every line carries the process key and event id.
- Metrics through Airflow's StatsD integration: events received, skipped (unchanged), sent, errors by kind, transport latency.
- `chappe` CLI reports component health and configuration problems.

## 12. Testing

### 12.1 Chappe's own tests

| Layer | Scope |
|---|---|
| Unit | Core, view helpers, watermark and write rules, key diff, engine with fakes, config validation, formatter |
| Snapshot | Every built-in theme × every sample run, reviewed as text diffs |
| Contract | Built-in components run the same conformance suites shipped to third parties |
| Property-based | Hypothesis: random event order, delayed writes, duplicates and drops; the final chat state equals a render of the final view; finished states are never overwritten; duplicate parents heal |
| Integration | Airflow 3 in CI running `examples/` in notifier mode against a local fake Slack server that records API calls and supports message metadata |
| End-to-end | Nightly, opt-in, real Slack sandbox workspace; never required for pull requests |
| Architecture | `import-linter`: `core` imports neither Airflow nor Slack; adapters do not import each other |

CI matrix: supported Airflow 3.x minors × their Python versions. Coverage floor on `core`.

### 12.2 Test kit (`chappe.testing`, a pytest plugin)

- **Sample runs:** every shape and state (single implicit section from a DAG without task groups, many sections, running, passed, failed, skipped) plus edge cases (unicode, very long names, 50 steps, empty sections), and `ProcessViewBuilder` for custom scenarios.
- **Conformance suites:** `ThemeConformance` in 0.0.1; `StoreConformance`, `TransportConformance`, `LinkerConformance` and `SourceConformance` in 0.0.2. Capability-aware: tests for a capability run when it is declared, and declaring it makes them mandatory.

```python
from chappe.testing import ThemeConformance

class TestMyTheme(ThemeConformance):
    theme = MyTheme
    tokens = "my_theme.yaml"
```

- **Snapshots:** `pytest --chappe-update-snapshots`.
- **Preview (0.0.2):** `chappe preview --theme metro --sample multi_failed` in the terminal; `--to slack:@me` sends it to the caller's DM.
- **Authoring guides** for themes, stores, transports and linkers; each checklist maps one-to-one to its conformance suite.

## 13. Engineering standards

- Python typed throughout, `mypy --strict`, `ruff` for lint and format, `pre-commit`.
- Supported versions: Airflow 3.x (minimum minor fixed after spike S4) and the Python versions that Airflow supports.
- Semantic versioning. Public API = `chappe` top-level exports, the port protocols, the run view, the message set, config schema and entry point groups. Breaking changes to contracts bump `contract_version` and follow a deprecation policy in CONTRIBUTING.
- Conventional Commits, `CHANGELOG.md`, tag-based releases to PyPI through trusted publishing.
- Architecture Decision Records in `docs/adr/`, starting with: ADR-0001 rebuild-and-reconcile rendering; ADR-0002 Slack metadata store and write rules; ADR-0003 notifier-first attachment; plus one per spike finding.
- Documentation site (MkDocs) with getting started, configuration reference, theme gallery, authoring guides and ADRs.
- Governance files: LICENSE (Apache-2.0), README, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY.

## 14. Roadmap

| Version | Scope | New capability |
|---|---|---|
| **0.0.1** | One real pipeline end to end: process-first config schema (one DAG per process enforced), core, `@milestone`, notifier mode, rebuild-and-reconcile engine with the write rules, Slack message-metadata store, Slack transport, `thread` and `plain` themes, `ThemeConformance`, `chappe validate-config` | none |
| **0.0.2** | What 0.0.1 trimmed: plugin mode (after performance testing, record-and-return listeners), `metro`, `now_next` and `tree` themes, the remaining conformance suites, `chappe preview` and `list-components` | none |
| **0.0.3** | Processes spanning DAGs, using the config shape shipped in 0.0.1: explicit process key (`link.key` template) plus automatic linking of triggered DAGs (trigger and asset links) | `MULTI_SOURCE` |
| **0.0.4** | Retries and repairs: attempt history in the thread, alerts only on final failure, repair announcements, recovery broadcast, resolved alerts edited | `ATTEMPTS` |
| Later | Postgres store with compare-and-set and a run-history recorder (all runs, step timings); Redis and object storage stores; mapped tasks; other transports; "View in Slack" extra link in the Airflow UI; sweeper for lost final events; optional duration charts | |

Themes declare which of these capabilities they support; the theme gallery documents it per theme.

## 15. Spike (before implementation)

Time-boxed, throwaway code, run on real Airflow 3. Output: a findings note, an ADR per decision, and a go/no-go. A finding that breaks an assumption sends the design back for review.

| # | Question | Decides |
|---|---|---|
| S1 | Which task field carries the `@milestone` marker through DAG serialization so the scheduler sees it? Do `task_display_name` and the task group's `group_display_name` exist on the minimum Airflow 3 minor and survive serialization? | Marker storage, title resolution |
| S2 | Where do task and DAG callbacks run in Airflow 3, and which API can each use to read other tasks' states in the run? | Source implementation |
| S3 | How efficiently can a bot find its own recent messages by metadata (paging, depth, rate limits under parallel runs)? Can it delete its own duplicate parent? | Slack metadata store, write rules |
| S4 | Minimum Airflow 3 minor for `BaseNotifier`, `task_display_name` and the provider entry point. (Plugin registration through provider info moves to the 0.0.2 spike.) | Packaging, supported versions |
| S5 | Moved to 0.0.2: how plugin-mode listeners record events and return, with rendering outside the scheduler; behavior across restarts and with several schedulers | Plugin mode |
| S6 | Slack rate limits for `chat.update` and thread replies per channel; `reply_broadcast` behavior | Backoff and throttling |

## 16. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Marker lost in serialization (S1) | High | Config-declared milestones via the `milestones:` override block |
| Hooks cannot read other tasks' states (S2) | High | Airflow REST API through a connection |
| A late writer overwrites newer state, or two parents are created | High | Write rules in 7.1 (watermark, sticky finish, final read-back, duplicate-parent healing); Postgres compare-and-set later |
| The parent message scrolls out of the scanned history on very long runs | Medium | Configurable scan depth; Postgres store for long-lived processes |
| Plugin mode slows the scheduler for every DAG | High | Not in 0.0.1; in 0.0.2 listeners only record and return, after performance testing |
| Listener or callback signatures change across Airflow 3 minors | Medium | Airflow code isolated in `integrations/airflow`; CI matrix; compatibility shims |
| Slack rate limits with many concurrent runs per channel (one extra read per event) | Medium | Backoff, per-channel throttling; measured in S3 |
| Final event lost, message left stale | Medium | Larger budget and retries; sweeper later |
| Third-party themes break on upgrades | Medium | Contract versions, capability checks, deprecation policy |
| Trademark | Low | Package `chappe`, product name "Chappe for Apache Airflow", no `airflow-` prefix |

## 17. Open questions

- How to represent parallel branches within a section in the run view and themes.
- Default scan depth for finding a process's message, and the wait before the final read-back.
- Representation of mapped tasks (out of scope; see Later).
- Default limits for parent message length and thread entry count.
